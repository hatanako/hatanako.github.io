## 为什么会有这个系列 
上班了之后，我发现一个非常严重的事情：

+ 一个小的系统模块非常简单，但是因为设计不当，UserData过度膨胀，牵引到了很多别的东西
+ 数据管理类职责太重，动不动就是上千行代码，读起来非常的困难
+ UI刷新的逻辑每个系统都不太一样，每个人都有每个人的写法
+ 有时候甚至找不到这里的逻辑到底是哪里的 

有些或许确实是代码写的不够规范，没有按照原有的架构去写。还有部分原因是，有些系统缺少了状态管理。所以导致了越来越难维护。  
这就是为什么我开始学习状态机，而不是选择继续堆功能的原因，也对应了我当时为什么要在类银开发日志里写**我们要进行重构，变为状态机模式**的原因。 

### Update为什么会越来越乱

刚开始做项目的时候，我很喜欢把逻辑直接写在Update里。因为方便快捷，见效快，我们可以非常快速的实现一个功能，看见效果，我认为这是正确的，没有任何错误，就好比：

```cs
public void Update()
{
    if(InputMove)
        Move();
    else if(InputJump)
        Jump();
    //.......其他逻辑
}
```

当你写了几个功能后，你会发现，一个玩家的类里面，既有移动、跳跃等实际逻辑，又有输入逻辑，甚至以后可能还有受伤、死亡等等数值改变的逻辑。  
这样就会出现一个问题，所有的功能都集中在一个类里面，一个player的Update方法里面就会有好几个管理逻辑：

+ 输入处理中心
+ 动画管理中心
+ 状态切换中心
+ 战斗逻辑中心

然后最后所有的逻辑都开始堆积在一个地方。

现在我们再来看这一块代码，目前只有Move和Jump，看起来还是非常清爽的，对吧。

但是当后面加上了：

+ 攻击系统
+ 闪避/格挡系统
+ 技能系统
+ 连击系统
+ 受伤/死亡

你会发现，要管的东西会指数级的增长。
后来我开始意识到： 真正的问题并不是“Update太长”。  
而是： “职责开始混乱”  
例如：  
输入系统负责什么？  
状态系统负责什么？  
动画系统负责什么？  
移动系统负责什么？  
如果这些边界不清晰： 系统复杂度会增长得非常快。

### 状态为什么是游戏核心 

首先是行为的切换的问题：攻击的时候可以做什么？不可以做什么？闪避的时候可以用技能吗？等等乱七八糟的问题。行为和行为之间开始冲突了。

这时候你会意识到“状态”的重要性：你会发现，像移动、攻击、待机、受伤、跳跃等等，都属于是一种状态，它决定了玩家当前在做什么，然后我们可以在这个状态里做限制，告诉系统：玩家在这个状态里可以做什么，不可以做什么。这样就变得清晰起来了。

所以，**状态机**本质上就是一套**行为管理系统**。

### 生命周期是什么

生命周期是一个很重要的概念：它决定了一个状态什么时候开始，什么时候结束，开始的时候需要什么，结束的时候需要清理什么。

这样我们可以很好的去划分一个状态，什么是该做的什么是不该做的。

因为实际上，很多bug都是因为生命周期混乱导致的。

比如： 原本只有移动和跳跃的时候，逻辑其实非常简单。  
但是后来加入了攻击系统之后，就会开始出现：

- 攻击时能不能跳跃？
- 跳跃时能不能攻击？
- 受伤时能不能释放技能？
- 闪避能不能打断当前动作？
- 技能期间输入是否缓存？

这个时候你会发现：  
逻辑已经不再是“单个功能”。  
而是： 功能之间的关系管理。  
这就是**生命周期**的作用。

### 为什么“行为”和“状态”不同

之前我一直认为： Move/Attack这些都是一个个行为，后来发现**行为**和**状态**是两码事。  
行为可能只是触发了一个动画，一个触发；  
而状态可能代表的是当前整个角色的行为约束，它不仅仅管理了动画，还包括了，能干什么，不能干什么，是否允许被打断等等。 ## 结语 以前我一直认为： 游戏开发最困难的部分，是“功能实现”。  
但随着项目越来越复杂，我开始慢慢意识到： 真正困难的，其实是：**如何管理复杂度。** 很多时候：功能本身并不复杂。真正复杂的是：

- 功能之间的关系
- 系统之间的边界
- 生命周期的管理
- 状态之间的切换

而状态机，只是我正式开始学习“游戏架构”的第一步。  
目前我只是刚开始接触状态机。 接下来我还会继续思考：

- 输入应该由谁管理？
- 状态是否应该直接控制动画？
- 状态切换是否应该允许打断？
- 如何避免状态数量爆炸？
- 玩家和AI是否可以共用状态机？

这些问题未来可能都会继续记录。

当然，状态机也不是万能的。

当状态越来越多的时候：

也会开始出现：

- 状态爆炸
- 状态切换复杂
- 状态依赖混乱

所以：

状态机本身也只是“管理复杂度”的一种方式。

而不是最终答案。
