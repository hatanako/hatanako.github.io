## 我发现，状态机并不是最终答案

为什么说状态机不是最终答案？在上篇文章中，我主要阐述了为什么项目复杂之后，会需要“状态管理”，但是当我真正开始写状态机的时候，我发现状态机也有很多不方便的地方。

我先是新建了一个工程文件，工程目录如下：

```text
Assets
└── Scripts
    └── GamePlay
        ├── Input
        │   └── PlayerInputHandler.cs
        │
        └── Character
            ├── Core
            │   └── PlayerController.cs
            │
            └── StateMachine
                ├── PlayerStateMachine.cs
                ├── PlayerState.cs
                ├── PlayerStateType.cs
                ├── IdleState.cs
                ├── MoveState.cs
                ├── AttackState.cs
                └── HurtState.cs
```

这个目录并不是为了“看起来高级”而拆出来的，而是因为我开始意识到：如果所有逻辑都塞进`PlayerController`，后面一定会再次变成一个巨大的`Update`。

所以我先粗略的拆成了三块：

- `Input` : 负责采集玩家输入
- `Core` ： 负责角色本体和组件引用
- `StateMachine`：负责角色当前处于什么行为阶段，以及状态之间如何切换

目前这个结构还很简单，甚至还有很多不完善的地方，但它至少让我第一次开始把“输入”、“角色本体”、“状态行为”分开看，而不是全部堆在一个脚本里，或者一个文件夹里。

在我目前写的这个状态机里：

`PlayerController`负责引用状态机、玩家和注册状态，它并不关心任何事情，只是作为一个中枢来把所有东西都连接起来。

`PlayerStateMachine`负责管理状态机，它主要进行切换正在运行的状态机，确保一直有一个状态存在。

`PlayerState`作为玩家的状态基类，所有的状态都是从这里衍生出去的，它有三个生命周期函数：Enter、Update、Exit。

这三个脚本基本上可以说是这个简单的项目的“地基”，后面所有的东西都在他们之上进行。

## 第一版状态机确实让结构变清楚了

在最开始的时候，我的感觉是：这个结构和之前把所有东西都写进`Update`，或者一个类里面，要清楚很多。

比如：

- 待机逻辑放在`IdleState`
- 移动逻辑放在`MoveState`
- 攻击逻辑放在`AttackState`  
等等

这样一来，`PlayerController`就不需要再知道“玩家现在到底应该怎么移动、怎么攻击、怎么受伤”了，它只需要把当前状态去交给状态机，让状态机判断更新就行了。

这一步确实解决了一个问题：把职责拆散了分散到了各个类里面，现在每个行为都有了自己的位置。

但是真的有这么方便吗？马上我又遇到了另一个问题，PlayerController确实不复杂了，但是随着状态的增多，每个状态之间的关系也越来越复杂了。

## 真正复杂的是状态之间的关系

当只有`Idle`和`Move`的时候，状态切换确实非常的简单：

- 没有输入时进入 Idle
- 有移动输入时就进入 Move

这个阶段几乎不会有什么架构压力。

但是当我加入`AttackState`之后，问题就开始出现了：

- 攻击时能不能移动？
- 攻击时能不能被移动打断？
- 攻击结束应该回到Idle，还是Move？
- 什么时候算攻击结束了？

这时候我才发现，状态机真正要管理的不是某一个状态本身，而是状态和状态之间的关系。

## CanExit 和 force 的出现

为了处理“攻击不能随便被打断”这个问题，我给状态加了一个`CanExit()`。

``` cs
public virtual bool CanExit(){
    return true;
}
```

攻击开始时，它应该持续一段时间，不能因为玩家按了移动键就立刻退出。所以在AttackState里，我让它在攻击结束之前返回false。

同时我又加了一个`force`参数，因为有些状态虽然不能被普通行为打断，但应该可以被**更高优先级**的行为打断，比如受伤。

相信你已经注意到了这个名词：**优先级**，是的，这就是状态机管理最重要的地方，总有状态是优于当前状态的，比如攻击位于Move、Idle之上，受伤位于攻击之上，死亡位于所有状态之上……

## 总结（暂时的）

写到这里，我认为这一篇文章差不多可以结束了，

一开始我认为，状态机就是用来解决角色的行为复杂度的，但是真正写起来我发现，它更像是把复杂度提炼了出来，摆在了一个更显眼的位置。

所以状态机并不是最终答案，它只是让我第一次开始正视：游戏里的很多问题，本质上不是单个功能的问题，而是行为之间的关系问题。

目前这个状态机还很粗糙。比如攻击结束还是靠时间判断，后面真正做战斗系统时，攻击状态应该更多的和动画、输入缓存、打断窗口联系在一起。

所以接下来我想继续研究的是状态机应该如何和动画系统配合。

因为对于动作游戏来说，真正决定一次攻击什么时候开始、什么时候取消、什么时候结束的，往往不是代码的计时器，而是动画和手感。
